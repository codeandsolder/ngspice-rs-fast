# Reusable optimization parameter binding and topology variation (#112)

## Ownership and invariants

- `netlist/eval/plan.rs` (#117) owns the only scoped dependency DAG. A new `ParameterPlan::bind_expression` uses its existing `RefScan`, including lexical `.func` free variables and aliases, to find the transitive *independent inputs* of a source site without introducing a second evaluator or a name lookup per candidate. `CandidateParameters::resolved_scope` publishes an evaluated lexical tree without parsing source or evaluating definitions again.
- `analysis/optimization/parameters.rs` compiles an immutable `CircuitParameterPlan` from the original `Netlist`, validates the ordinary scalar baseline circuit and site evaluation, and retains typed binding recipes for numeric device setters. The circuit owns the sole `DeviceNames` index, `InstanceTarget` is the existing topology-scoped binding from #134, and no `.dc` sweep axes are invented.
- `CircuitParameterPlan` is shareable by independent sessions: it does **not** retain mutable solver state or a `Circuit` with `RefCell` caches. Each `session()` builds its own finalized baseline circuit, binds its own typed targets once to that circuit's unique identity, and holds independent mutable `CandidateParameters` values.
- Every candidate `update` clones only numeric session state for staging, checks the whole candidate vector, updates the existing DAG in dependency order, evaluates potentially changed source sites, validates effective device physics and topology, and publishes all changes only after success. An invalid candidate preserves the previous vector, context, circuit and result identity. Calling `update` with identical binary64 coordinate bits is a no-op.

## Fast route and scalar route

The fast route requires **all** affected source sites to be device scalar assignments whose ordered C setter semantics can be represented by an existing typed `InstanceTarget` at the prepared circuit's current topology. The current provably safe bindings are resistor supplied resistance (including model-backed thermal recipes) and independent source DC, plus supported non-model instance setters. Repeated later setters, models whose own declarations depend on parameters, subcircuit/formal expansion, behavioural rewriting, model bin geometry, options, output syntax and analysis requests are not guessed from the scalar's name. They take the general scalar-equivalent re-elaboration route if affected.

On the fast route, a site expression is only evaluated if its compiled dependency closure contains a coordinate differing from the plan baseline. Its value is first converted using the *same* `format_literal` and `parse_spice_number` as the normal numparam literalization stage. If its read-back bits equal the baseline, no override is inserted. Otherwise a bound `InstanceTarget` inserts a value into `ModelContext`, retaining the independent res/source override ordering. `Circuit::validate_candidate_context` invokes the same replacement, model-validation and layout invariants used by the actual assembly path. Previous analysis state is cleared on successful candidate transitions, while the stable finalized node/branch numberings and sparse-pattern allocation survive.

**Full analysis execution, not just matrix preparation:** the candidate's `analysis_context()` contains the candidate's topology-scoped typed overrides, overlaid on the ordinary `RunConfig::context()` temperature/tolerances/pivot. `AnalysisContext::model_context()` copies only the resistor/instance override slots from that candidate, retaining its *current analysis* frequency/temperature/gmin settings, so `.op`/`.ac`/`.tran`/`.noise` and existing objective-run drivers see the same candidate as low-level `linear_system_with_context()`. The candidate's `config()` includes the newly resolved `.param` scope; measurement and analysis-expression evaluation therefore see the candidate's scalar values, not the original baseline. Use `candidate.circuit_mut()` together with `candidate.analysis_context()` to run analyses; passing the original baseline `RunConfig::context()` to an optimizer's driver intentionally does not install candidate overrides.

The fast `ModelContext` is currently restricted to two independent resistor and two independent instance overrides because its *existing* fixed slots were designed for two-axis `.dc`. That capacity is not an optimization vector-size limit: candidates with more affected values use the general validated route, which supports arbitrary numbers of independent inputs. Invalid domain, duplicate alias-folded setters or changed state/branch topology are never silently accepted. Failure to represent a candidate as a typed overlay triggers scalar re-elaboration; if the scalar factory rejects the candidate too, the previous candidate remains current. A new dynamic override vector can replace the capacity fallback in a separate optimization without changing correctness.

The general route materializes the already evaluated lexical parameter scope, resolves `RunConfig` options and node hints against it, and calls the ordinary circuit lowering, literalization, nested subcircuit expansion, model-bin selection, generated-node assignment, geometry and state-layout validation. No netlist text reparse, no globally cached stale topology, no wrapper compatibility path. Even when two candidate topologies happen to have identical node names, a re-elaborated circuit gets a *new* topology identity; its solver/observation handles must be rebound. `CircuitCandidate::topology` distinguishes `Reused` versus `Rebuilt`, and `circuit_mut()` exposes an independent circuit for ordinary simulation drivers.

## Error and concurrency contracts

- Candidate vector length and finite inputs are validated by `CandidateParameters::update`. Derived parameter domain errors, evaluation-budget exhaustion, invalid instance/model physics or unrepresentable effective values cause transactional rejection.
- A failed update leaves the previous candidate context, `Circuit`, `RunConfig`, source/solver state and parameter values intact. A successful candidate transition clears previous accepted/transient state; only validated immutable topology and sparse assembly pattern remain.
- Independent sessions may be used by parallel optimizer workers. `ParameterPlan`/`CircuitParameterPlan` contain immutable source and dependency data, no global memoization; each lane owns the graph's staged numeric state and its own mutable `Circuit`.
- Numerical equivalence must be compared **against separately elaborated scalar decks**, including current `.option` temperature and model-bin decisions. Reusing a cached MNA pattern or state layout after a structural change is categorically forbidden, regardless of its apparent performance benefit.

## Tests and metrics

`tests/optimization_parameters.rs` covers typed source/resistor overlays versus separately elaborated linear matrices, RHS and full `.op` driver results through A/B/A, failed candidate atomicity, arbitrary 4D resistor candidates falling back safely, `.model` and temperature updates rebuilding, `.func` captures and alias input reduction, and parallel independent sessions. The older `tests/optimization_parameter_plan.rs` exercises nested lexical `.param` scopes, shadowing and aliases, dirty propagation, invalid candidates, signed zero and independent-session semantics. Test compile and strict lint use the campaign-pinned nightly, managed sccache and per-worker build directory.

For performance measurement, compare repeated `CircuitCandidate::update` (including the actual changed site and effective device preflight) against independently calling `Circuit::from_netlist`/`RunConfig::circuit` on a series of scalar-equivalent decks of the *same* model and size. Report preparation-only allocation count, throughput, per-site affected DAG nodes, new topology frequency and elapsed simulation time separately. The purpose of the fast route is removing repeated parser/expansion/model work when the selected physical model's structure is unchanged; no performance claim should be made until measured.
